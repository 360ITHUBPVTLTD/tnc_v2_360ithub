01 · Overview

Overview

What the institute does, what the system is for, and how the pieces fit.

The institute

TNC is a coaching institute running offline batches at the centre and online live batches for competitive-exam students. A prospect comes in as an enquiry, takes a demo class, is admitted into a batch and pays the agreed fee in instalments. Teachers are paid for approved timesheets, less any penalties. Staff log tasks, expenses and their own attendance from a mobile app.

Admissions

Enquiry to enrolment

Enquiry, follow-ups, demo, admit, batch enrolment, Sales Order.

Fees

Instalments & receipts

Payment schedule, follow-ups, receipt invoice per payment, outstanding.

Attendance

Machine to daily record

Biometric punches, Present / Late / Absent, automatic hold.

Teachers

Timesheets to payment

Approval, syllabus progress, invoices, penalties, weekly settlement.

Staff

Tasks, expenses, HR

Recurring tasks, digest, expense review, check-in, payroll-ready HRMS.

What the system solves

  • One funnel — every student starts as an enquiry; the counsellor who converted is stamped for incentives.
  • Fees on standard accounting — committed fee is a Sales Order, every payment a receipt invoice; outstanding is never a spreadsheet.
  • No manual attendance marking — the biometric machine is the record; staff only correct, with remarks.
  • Holds that follow the enrolment — a student in two batches is blocked only where they are absent.
  • Teachers paid from approved work — penalties recovered at payment time, never by hand.
  • One task system — three generations of v1 task doctypes replaced by standard Task with v1's recurrence engine.
  • Everything configurable — thresholds, approvers, numbers and switches live in settings, not in code.

04 · Business Requirements (BRD)

BRD — what the business needs

Each requirement states the problem in v1, what the business needs, how we know it is met, and its status. Grouped by Scope-of-Work section.

Objectives
  • Replace the v1 customisations with a designed system on standard ERPNext.
  • Track every student from enquiry to completion with fees on the ledger.
  • Attendance from machines, holds without manual chasing.
  • Teacher pay and penalties from approved work, not spreadsheets.
  • One mobile app for staff and teachers.
Scope & stakeholders
  • Scope: the Scope of Work of 14 Aug 2026, 14 sections; one agreed addition (digital admission form).
  • Client side: management (Bhojraj), office and counsellors, teachers, Finance.
  • Vendor: 360ITHub (Pankaj, Anurag; app builds by Apurba).
  • Out of scope: anything not in the SOW; FRD items are built only after their rule is frozen.
05 · Functional Requirements (FRD)

FRD — how the system does it

Each function: who uses it, where it lives, what the system does, the rules it enforces, how to test it, and where the code is.

Non-functional requirements

  • No hardcoding — names, amounts, thresholds, sheet ids and approvers come from masters and settings; imports match against masters and report misses.
  • Upgrade-safe — standard doctypes are extended with custom fields (prefix custom_) and hooks; own doctypes via JSON; every core deviation registered.
  • Testable — each module has a flow test script that runs on the dev site and cleans up after itself.
  • Auditable — submittable documents where money moves; Track Changes and mandatory remarks where staff correct a machine record.
  • Same domain — live stays on tnc.360ithub.com so the app, the machines and the WhatsApp webhook never change address.
  • Nothing changes on live without a human — migrations are run by the server admin from a release note; never from a developer's machine.

What happens when a user saves / submits a document

  1. Frappe runs the doctype controller: validate, then before_save / on_update / on_submit.
  2. Hooks in doc_events run after the controller for standard doctypes (for example the Task notification hooks).
  3. Submitted documents never run validate again; rules for later edits go in before_update_after_submit (enrolment hold release does this).
  4. Side effects that create other documents (Sales Order on enrolment submit, Sales Invoice on payment, Purchase Invoice from timesheets) happen in the controller and are undone in on_cancel.
  5. Notifications go through notifications.py, which checks the settings switches and logs every WhatsApp send.

Who sees which records

  • Teachers see only their own timesheets, penalties and payouts (user permission on Teacher, set on migrate).
  • Penalties have a permission query: imposers, approvers and the teacher concerned.
  • Employees see their own expense claims and tasks assigned to them; managers see their team's.
  • Public pages (/enquiry, /admission, /demo-feedback) run as Guest, locked to a signed, single-use, 48-hour link.

5 · Rules & conventions

  • Own doctypes: edit the JSON in the app, then local migrate. Standard doctypes: Customize Form, fields prefixed custom_, exported into the app.
  • No hardcoded names, ids, amounts or lists. Match against masters; report what did not match.
  • Settings switches default to off. A message is never sent unless the switch is on and a number exists.
  • Messages to users start with "Dear <name>," and never name internal screens.
  • Test data you create, you remove. Flow tests end with a cleanup count.
  • One repository per app; the workspace repo holds specs, ADRs and this guide's facts.
  • Branch per developer and date (for example Anurag16Sept); the user merges and pushes.
  • Release note before any live change: which apps move, the commands, who ran them, what was checked.
  • Every deviation from upstream core goes in docs/core-modifications.md, append-only.
  • Write plain explanations for the client; plan before build; show the form before the next step.
